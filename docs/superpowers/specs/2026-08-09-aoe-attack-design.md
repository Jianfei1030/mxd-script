# 群攻 —— 接敌区内怪数达阈值时改用双向技能

日期：2026-08-09
状态：已实现（`feat/aoe-attack`）。§3.1 / §3.4 / §3.7 于 2026-08-10 按实现期发现的问题修订过，见各节标注
上游：`2026-08-07-directional-attack-zone-design.md`（接敌区/攻击区两分，本设计的计数区就是它的接敌区）、`2026-08-06-attack-zone-mob-gating-design.md`（攻击区与锚点）

## 1. 问题

现在只有一条输出路径：`_do_attack`（`MapleFarmTask.py:827`）按 `攻击间隔` 轻点唯一的 `攻击键`，打的是**有向攻击区**（接敌区的面朝侧一半，`farm_logic.facing_half_zone`）。

被怪围住时这条路径有两个结构性损失：

1. **背侧的怪打不到。** 有向攻击区只覆盖面朝侧，背后那一半怪只能靠转向去打，而转向受 `转向冷却(秒)`（默认 1.5）限制 —— 与默认 `攻击间隔(秒)=1.5` 齐平，用户实机把攻击间隔调到 0.7 时更是长一倍（实跑配置见 `2026-08-07` spec §3.1）。
2. **转向本身在消耗节拍。** 区内两侧都有怪时，`attack_turn_direction` 的目标侧锁定只在面朝侧真空后才换边，但换边那一拍要付一次方向键 tap + `self._last_detect = 0.0` 作废检测节拍（`:694`）。怪多的时候这种拍不罕见。

冒险岛的群攻技能（前后双向命中）恰好对上这两条：它不需要朝向，一发覆盖两侧。

**注意 `攻击区形状=群体(对称)` 不是这个功能。** 它只是把有向区退回对称区，**按的还是同一个 `攻击键`** —— 那是有向攻击区改动的安全退路，不是「换技能」。群攻是一个独立技能槽、独立按键，但**共用同一条攻击节拍**（§3.1）。

历史实测（`2026-08-07` spec §3.1，本次未重测，仅用于定阈值）：`800×200` 的接敌区里**平均区内怪 0.36 只、有怪帧占 28%、两侧都有仅 6%**。

## 3. 设计

一句话：**攻击节拍到点时，接敌区内怪数 ≥ 阈值且群攻键已绑 → 按群攻键，那一拍不转向、也不按单体攻击键。其余一切照旧。**

### 3.1 配置变更

| 键 | 位置 | 默认 | 说明 |
|---|---|---|---|
| `群攻键(可留空)` | `config.py` 全局「游戏按键」 | `''` | 群攻技能键。留空 = 功能关闭 |
| `群攻怪数阈值` | 任务配置 | `3` | 接敌区内怪数达此值改用群攻 |

**留空 = 关闭，不另设开关键。** 与 `椅子键(可留空)` / `宠物食物键(可留空)` / `回城卷键(可留空)` 同一约定。

**阈值 3 的依据（原始，纸面推理）**：§2 的历史实测里「两侧都有怪」只占 6%，`平均区内怪 0.36`。阈值设 2 会让「一左一右两只」这种常见局面天天触发群攻 —— 那不是群攻要解的场景，转向一次就够。3 是「确实被围住了」的起点。

**2026-08-10 实测推翻了上面这段的结论。** 功能上线后第一次实机挂机（`logs/ok-script.log`，19:44:43–19:49:26，359 个检测拍，`攻击间隔=0.7`）的 `区内=N` 分布：

| `区内=N` | 拍数 | 占比 |
|---|---|---|
| 0 | 281 | 78.3% |
| 1 | 59 | 16.4% |
| 2 | 17 | 4.7% |
| **3** | **2** | **0.6%** |

阈值 3 在真实刷图里 4.7 分钟只生效 **2 拍**——不是「天天触发」，而是**几乎从不触发**。原推理错在把「屏幕上有 3 只怪」当成了「接敌区内有 3 只怪」。

原因在决策行里看得很直接，例：`怪=3 区内=0(左0/右0) 近怪dx=-854 dy脚=+566 dy心=+590`。把「屏幕有怪但 `区内=0`」的 281 拍按最近怪的垂直距离分桶：

| \|dy心\| | 拍数 | 含义 |
|---|---|---|
| ≤100（接敌区高度半幅） | 41 | 高度对得上，横向超出 ±300 |
| 101–300 | 66 | 略高/略低 |
| **>300** | **174（62%）** | **根本在别的平台上** |

接敌区默认 `600×200`（±300 横 / ±100 纵），而 §2 那份历史实测是在 `800×200` 上做的 —— 默认区比它更小，`区内=3` 因此比那份数据预示的还要罕见。

**结论**：阈值降到 2 可把覆盖率从 0.6%（2 拍）提到 5.3%（19 拍）。代码里的默认值**暂时仍是 3**，等 §5.3 判据 B 的绑定/留空对照跑完再定 —— 覆盖率高不等于经验高，那正是 B 要测的东西。不建议先动 `攻击区宽/高`：接敌区同时门控转向/寻怪/坐椅/走位，它的面朝侧一半还是单体攻击区，爆炸半径远大于这个功能。

**为什么群攻没有独立节拍**（2026-08-10 修订，原设计有一个 `群攻间隔(秒)=2.0`）：群攻与单体**共用 `攻击间隔(秒)`** —— 节拍到点了，看接敌区内怪数决定按哪个键。原来给它独立节拍的两条理由后来都不成立：

1. **「群攻耗蓝是单体数倍，共用会瞬间空蓝」** —— 用户判定耗蓝不是问题，这条作废。
2. **「独立节拍保护群攻施法窗」** —— 站不住。单体自己就在 `攻击间隔=0.7` 下自断施法（施法时长 0.7–1.0s 是实测的，见 `2026-08-08-facing-observer-design.md:66`），群攻并不特殊；而「群攻施法约 1 秒」这个数从没测过，是类比估的。更要紧的是**代码里根本没有施法窗模型**——`_busy_until` 在那份 spec §6「本设计不实现」里被显式推迟，全库无此变量。

而独立节拍有确定的代价：两个节拍互质地各走各的，相位任意，群攻会落在上次单体后 **0.6s**（< `攻击间隔` 0.7），即落在用户自己声明的单体施法时长之内。共用一条节拍从构造上消掉这一整类问题，还少一个旋钮。

原 §3.7「群攻同时推进 `_last_attack`」随之改变性质：那一行不再是「顺带保护施法窗」，而是这条路径**自己的**节拍记账，漏写会让群攻每个 10Hz 拍连发。

### 3.2 计数区 = 接敌区，不新增区

数**接敌区**（对称，`攻击区宽(像素) × 攻击区高(像素)`）里的怪，判定点仍是**框中心**（`point_in_zone`，与 `mob_in_zone` 同源）。

不新增 `群攻区宽/高`，理由同 `2026-08-07` spec §4.5「不新增射程参数」：群攻真实范围**从没标定过**，现在加两个旋钮只是把未知包装得更精致，还多两个要维护的参数。

且不同源会引入一类难查的状态：「群攻区里 5 只、接敌区里 2 只」——而转向/寻怪/坐椅/走位全都吃接敌区，两个区打架的排查成本远高于收益。等实跑出现「区内 4 只却打不到」，再用 `scripts/calibrate_attack_zone.py` 标出真值拆参数。

### 3.3 纯函数

```python
def crowd_present(mob_count, threshold):
    """接敌区内怪数达到阈值 → 该用群攻。threshold <= 0 视为关闭(恒 False)。"""
    return threshold > 0 and mob_count >= threshold
```

节拍复用现成的 `should_attack(now, self._last_attack, cfg['攻击间隔(秒)'])`，不新写节流函数、也不新增节拍状态（§3.1）。

### 3.4 单一判据 `_aoe_ready(cfg, keys, now)`

转向门与攻击门**必须用同一个表达式**，否则会出现「以为要群攻所以没转向，结果群攻没发」这种两头落空的拍。所以抽成一个方法，两处都调它：

```
攻击模式 == '检测'
且 群攻键(可留空) 非空
且 self._last_zone_count_time == now                    ← 计数必须是本拍现测的
且 farm_logic.crowd_present(self._last_zone_count, cfg['群攻怪数阈值'])
且 farm_logic.should_attack(now, self._last_attack, cfg['攻击间隔(秒)'])
且 not farm_logic.stun_suppressed(now, self._last_hit, cfg['硬直抑制窗(秒)'])
```

`_detect_and_act` 与 `_do_attack` 在同一 tick 内被同一个 `now` 调用，期间没有任何代码写 `_last_zone_count` / `_last_zone_count_time` / `_last_attack` / `_last_hit`，所以两次求值必然同值。这是「同一拍不转向 ⟺ 同一拍真发群攻」的正确性前提，实现时不许把其中一处换成别的写法。

**计数新鲜度门**（2026-08-10 补，修的是实现里已存在的一个缺陷）：`_do_attack` 每个 10Hz 拍都跑，而 `_last_zone_count` 只在**检测拍**写（检测拍受 `should_detect` 节流）。没有这道门，怪清光之后的非检测拍会拿着上一个检测拍的旧计数放空群攻。实测复现（默认 `攻击间隔=1.5`）：

```
t=100.0 检测拍 count=3 → 发群攻
t=101.5 检测拍 count=3 → 节拍未到，不出键
t=101.6 怪被清光
t=102.0 非检测拍 → 读到 0.5s 前的 count=3，朝空区又发一次群攻
```

这正是 §3.10「计数不去抖」明确要避免的「怪清光后仍按旧计数多放一发空群攻」——逐拍求值把一个宽度 = 一个检测周期的保持窗从后门放了回来。转向门那次求值天然满足这道门（它就在写完计数的几行之后），所以门只对 `_do_attack` 起作用。

> 复现时注意：怪若在背侧，那一拍的转向会把 `_last_detect` 清成 `0.0` 哨兵，反而让下一拍变回检测拍、把陈旧计数刷掉，看起来像没问题。把怪放在面朝侧才稳定复现。

> 不用 `_last_detect == now` 做这道门：转向那一拍的 `_last_detect = 0.0` 会让 `_detect_and_act` 与 `_do_attack` 两次求值读到不同的 `_last_detect`，正好破坏上面那条「必然同值」的前提。

### 3.5 接线

**`_detect_and_act`**（`:584`）：
- 算完 `zone`（`:606`）与 `centres` 之后，取区内怪（框中心落在 `zone` 内）写 `self._last_zone_count = len(in_zone)`；阈值判定留给 `_aoe_ready`
- 这个 `in_zone` 列表顺手传给 `_log_decision`，取代它现在自己重算的那一份（`:753`）——同一个数被算两遍是将来漂移的种子
- 转向门加一项：`if turn is not None and not self._aoe_ready(...) and turn_allowed(...) and ...`

**`_do_attack`**（`:827`）：群攻优先，二选一。

```
if self._aoe_ready(cfg, keys, now):
    send_key(群攻键); self._last_attack = now; return
<原单体逻辑一个字不改>
```

**新状态**（进 `_reset_state`，`:212`）：`_last_zone_count = 0`（最近一次检测拍的接敌区内怪数，`0` = 还没检测过）、`_last_zone_count_time = None`（那个计数是哪一拍测的，`None` = 还没测过）。

不再有 `_last_aoe`：群攻走共用节拍，节拍由 `_last_attack` 一处记账（§3.1）。

存**计数**而不是布尔 `_last_crowd`：少一个要同步的状态；阈值在 `_aoe_ready` 里**用时现读**，GUI 改 `群攻怪数阈值` 立刻生效，不用等下一个检测拍；日志行（§4）也正好要这个计数。

### 3.6 群攻拍不转向

群攻双向命中，转向对它零收益，而代价是实打实的：一次方向键 tap + `self._last_detect = 0.0` 作废检测节拍（`:694`）。

**只在真发群攻的那一拍跳过转向**，节拍间隙的拍照常转向。不做「crowd 成立就整段禁转向」——那样节拍间隙里如果怪全在背侧，单体攻击区（面朝侧半区）是空的，角色会面朝空处站着挨打。

副作用（是好事）：群攻拍 `_facing` **完全不动**，不会出现「群攻拍盲写了朝向、下一拍单体按着错朝向打空」这种新分叉。

### 3.7 群攻推进 `_last_attack` = 共用节拍的记账

（2026-08-10 修订：本节原来的理由是「群攻施法约 1 秒，不推进的话单体键会落在群攻施法中间把它打断」。那条理由随独立节拍一起作废，见 §3.1 —— 而且它自己也不成立：推进只买到一个 `攻击间隔`（0.7s）的保护，比它声称要保护的 ~1s 施法还短，实测时间线 `t=100.0 群攻 → t=100.7 单体` 就落在那 1 秒之内。）

现在这一行的作用是直白的：**群攻与单体共用一条 `攻击间隔` 节拍，谁出手都由 `_last_attack` 记账**。漏写的后果不是「单体打断群攻」，而是群攻每个 10Hz 拍连发。

推论：区内怪数持续达阈值时，每个节拍都是群攻，单体整段不出场（二选一，群攻优先）。这是有意的 —— 群攻双向命中，被围住时它严格优于「转向 + 单体」。

### 3.8 寻怪与群攻天然互斥，不写额外门

`crowd` 成立 ⇒ 接敌区内有怪 ⇒ `raw_present` 为真 ⇒ `seek_hold` 为真 ⇒ 走接战分支。所以「一边追一边放群攻」在结构上不可能发生，不需要新分支。

但这是个**隐式**不变量，要写一条测试把它钉死（§5.2 用例 i），否则将来有人改了 `seek_hold` 的算法就会静默破掉。

### 3.9 行为矩阵

| 接敌区怪数 | 群攻键 | 攻击节拍 | 行为 |
|---|---|---|---|
| ≥ 阈值 | 已绑 | 已到 | **按群攻键；不转向；不按单体攻击键** |
| ≥ 阈值 | 已绑 | 未到 | 照常转向；不出任何攻击键（节拍共用，单体也没到） |
| ≥ 阈值 | 留空 | — | 逐键等同改动前 |
| < 阈值 | 任意 | — | 逐键等同改动前 |
| 攻击模式 = 定频 | 任意 | — | 逐键等同改动前（没有找怪信息，无从计数） |

### 3.10 计数不去抖

YOLO 单帧 recall 0.886，4 只可能读成 3 只 —— 但这只会**漏触发一拍**（延迟 ≤ 一个检测拍），不会误触发。反向的「怪清光后仍按旧计数放空群攻」由 §3.4 的计数新鲜度门挡住。

反过来，加保持窗会把「被围」状态撑长：怪已清光却还按旧计数多放一发空群攻，浪费的是蓝。阈值本身就是旋钮，不需要再叠一层去抖。

（这与 `丢怪保持`/`寻怪保持` 的取舍方向不同，是因为那两处的失败代价是「停手/停步」，而这里的失败代价只是「晚一个检测拍放群攻」。）

## 4. 可观测性

**不动 `decision_log_line`。** 它是决策行格式的唯一事实源，`scripts/analyze_facing.py` / `scripts/analyze_seek.py` 的正则和一批绑定测试都吃它；为一个布尔值改格式不划算。区内怪数本来就有 `区内=N` 字段，阈值分布可以离线算。

**新增 `aoe_log_line(count, threshold)`**，每次**真按下群攻键**写一行（照「受击」那行的先例，同为格式唯一事实源）：

```
群攻 区内=N 阈值=M
```

判据直接 grep「群攻」。

**overlay**（`_draw_debug`，`:511`）：接敌区框在群攻就绪时线宽 `1 → 3`、标签由 `接敌区` 改为 `接敌区(群攻)`。这是判据 D 的视觉验收对象。

就绪标志由 `_detect_and_act` **求值一次**、作为新参数（`aoe_ready=`）传进 `_draw_debug`，与既有的 `mob_present=` / `attack_present=` 同一写法。不在 `paint` 闭包里再调 `_aoe_ready` —— 闭包是 Qt 重绘时才执行的，那时 `now` 已经过去，会画出与决策不一致的框。

### 5.1 纯函数单测（`tests/test_farm_logic.py`）

`crowd_present(mob_count, threshold)`：
- `(3, 3)` → True（**等于阈值算命中**）
- `(2, 3)` → False
- `(4, 3)` → True
- `(0, 3)` → False
