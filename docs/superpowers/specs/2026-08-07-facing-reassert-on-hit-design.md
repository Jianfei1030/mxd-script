# 受击后重申朝向 —— 修「被打之后背对怪挥空且不自愈」

日期：2026-08-07
状态：设计已确认，待实现
上游：`2026-08-05-ok-mxd-design.md`（MVP 设计）、`2026-08-06-attack-zone-mob-gating-design.md`（攻击区与锚点）

## 1. 问题

用户报告：**被怪打之后，角色会背对着怪一直挥空，而且长时间不自己纠正过来**。

这不是「转向太频繁」（2026-08-07 已排查过的老症状，另见 §3.3），是它的反面 —— 该转的时候一次都不转。

## 2. 现状盘点：为什么不自愈

`_facing` 是**纯信念状态**，不是观测量。它只有三个写入点，全部是「我们自己按了方向键，所以认为角色转过去了」：

| 写入点 | 位置 | 场景 |
|---|---|---|
| 转向轻点后 | `MapleFarmTask.py:457` | 站桩接战换边 |
| 走位第二段方向 | `MapleFarmTask.py:508` | 防挂机走位 |
| 寻怪长按方向 | `MapleFarmTask.py:575` | 追怪 |

游戏侧任何**不是我们发起**的朝向变化，都不会写回信念。

锁死的确切链条：

```
_facing = 'RIGHT'（信念）        实际角色朝左
怪在身体右侧（真实位置）
  ↓
attack_turn_direction(facing='RIGHT', ...)   farm_logic.py:239
  → 目标侧锁定：「面朝侧攻击区内还有怪」→ 返回 None，不转
  ↓
_do_attack 照常按攻击键 → 打在左边空处
  ↓
下一拍完全相同 → 永不自愈
```

根因是这个判定**只比对「信念 vs 怪的位置」，永远发现不了「信念 vs 现实」的分歧**。目标侧锁定本身是对的（它解决了 38% 换边率的老问题，§3.3），但它以信念可信为前提。

现有的 `_key_sendable()`（`MapleFarmTask.py:320-331`）挡不住这个：它调用 `executor.interaction.clickable()`，只能知道**窗口有没有焦点**，看不出游戏因为别的原因丢了这个键。

## 3. 证据

### 3.1 本次实测（2026-08-07，读代码 + 24 帧图像实验）

| 事实 | 出处 |

| 主循环 10Hz；检测拍按 `攻击间隔(秒)`（默认 1.5）节流 | `MapleFarmTask.py:719`、`:19` |

| `_detect_and_act`（可能转向并更新 `_facing`）在 `_do_attack` **之前**执行，同一 `run()` 拍共用同一个 `now` | `MapleFarmTask.py:719` vs `:727` |

| 参考项目 MapleStoryAutoLevelUp **不跟踪朝向**：攻击时把方向键一起发出去 | `_reference/.../MapleStoryAutoLevelUp.py:1517-1521` |

角色朝向的模板匹配可行性也在本次做了 24 帧实测，结论是「可行且判别裕度很大」，但本次**不实施**，数据完整保留在附录 A。

### 3.2 关键推论：寻怪路径已经自愈，缺口只在站桩攻击

`_do_seek_move` 每个检测拍都重按方向键，等于持续重申朝向；追怪途中信念就算错了也会被下一拍的按键覆盖回来。

站桩攻击这条路上没有任何东西会重按方向键 —— `_do_attack` 只按攻击键（`MapleFarmTask.py:543-561`）。**这就是 bug 的唯一缺口。**

### 3.3 历史实测（前序会话，直接引用，本次未重测）

这几条决定了「什么方案不能选」：

- 转向 17 次里 12 次是反向翻转，序列 `LLLLRLRLRLRLRLLRL`（2026-08-07 逐拍日志，363 拍/188 秒）
- 每拍重选最近怪 → 相邻采样换边率 **38%**，且与攻击区宽无关（1200→800 实测 39%→38%）
- **已验证无效，别再试**：转向冷却 1.5s（反向 12→9）；「侧占用去抖」（反向反而 12→19）
- 挥砍中 `body_x` 跳变 >80px 的拍占 **19%**（其余状态仅 5%）= 挥砍时被击退非常频繁
- 离线重放量不了这题：`dataset/raw/*` 是 2 秒一帧，翻转发生在 0.1-0.7s 尺度

### 3.4 待验证假设（不许当结论用）

**核心假设：`_facing` 漂移是因为受击硬直吞掉了我们发出的方向键。**

即：被打 → 角色进入受击/击退硬直 → 这期间我们发的转向轻点被游戏忽略 → 但 `_facing` 照样推进 → 信念与现实分歧。

支持它的间接证据：症状发生在「被打之后」（用户报告）；挥砍时被击退频繁（§3.3 的 19%）；`_key_sendable()` 检测不到这类丢键（§2）。

**但这没有被直接验证过。** 另一个同样能解释症状的机制是「游戏在受击时把角色翻向攻击者」。两者都指向「受击时刻 = 信念失效时刻」，所以本设计对两者都成立；但如果真实原因**两者都不是**（例如游戏在别的情况下自行转向），本设计就无效。

§6 的日志字段和 §7.3 的判据 A/B 就是用来证伪这个假设的。

其余待验证：
- 「受击到下一个攻击拍平均 0.75s」是否足够躲过硬直 —— 硬直时长未测
- HP 降幅阈值 0.01（≈2 列）是否躲得开读数抖动 —— 未测抖动幅度
- 50ms 轻点在「不换边、单向重复」下是否会累积位移到走出站桩点 —— 未测

## 4. 设计

一句话：**HP 掉了 → 在下一个攻击拍，按攻击键之前，朝当前 `_facing` 侧重新按一次方向键。不换边。**

### 4.1 受击检测

主循环拿到 `hp` 之后立刻比较并更新，位置在 `MapleFarmTask.py:644-645` 与死亡判定之间：

```
hp < _last_hp - HIT_HP_DROP_EPS   →  _last_hit = now
_last_hp = hp                     （无条件更新）
```

- `HIT_HP_DROP_EPS = 0.01`（≈2 列，躲开单列抖动）
- `_last_hp` 初值 `None`，首帧只记录不判定
- 喝药、坐椅回血、升级都是 HP **上升**，天然不触发

**已知误报**：HP 条被弹窗遮挡时的单帧误读会造成假受击（死亡判定的注释里记过这种误读存在）。代价是多发一次 50ms 方向轻点、方向还是原方向 —— 可以接受，不为它加确认帧数。

### 4.2 重申时机与条件

在 `_do_attack` 里，**决定要按攻击键的那一拍**，先重申再攻击：

```
_do_attack:
    区内有怪 且 到攻击间隔:
        _reassert_facing(...)      ← 新增
        send_key(攻击键)
```

`_reassert_facing` 五个门，全过才发键：

| 门 | 条件 | 理由 |
|---|---|---|
| 开关 | `受击后重申朝向开关` 为真 | A/B 对比用 |
| 有边可重申 | `_facing in ('LEFT','RIGHT')` | `None` 时没有边可宣示，交给 `attack_turn_direction` 的最近怪回落 |
| 在受击窗口内 | `last_hit > 0.0` **且** `now - last_hit <= 3.0` | `last_hit <= 0.0` 是「从未受击」哨兵，必须**显式判**：单靠 `now - 0.0 > 3.0` 在真实时间戳下成立，但单测里传小 `now` 就会假通过 |
| 本拍没转过向 | `_last_turn != now` | 本拍 `attack_turn_direction` 已经转过向的话，那次轻点本身就是重申，不重复发。浮点相等在这里成立：`_detect_and_act` 与 `_do_attack` 在同一 `run()` 拍里共用同一个 `now` 变量（§3.1） |
| 键发得出去 | `_key_sendable()` | 与现有朝向写入守卫一致 |

发的键：`_facing == 'LEFT'` → `左移键`，否则 `右移键`，`down_time=TURN_TAP_SECONDS`（50ms）。

**不写 `_facing`** —— 重申发的就是当前信念的方向，信念不变。

### 4.3 三个设计要点

1. **不换边，只重申**。选边规则（`attack_turn_direction` 的目标侧锁定）一个字不改，因此**不可能引入 §3.3 那种左右交替** —— 那些失败方案全都动了选边规则。
2. **挂在攻击拍上，不用独立定时器**。频率被 `攻击间隔`（1.5s）天然封顶，不会刷键；受击到下个攻击拍平均 0.75s，天然等过了硬直，不需要额外延迟逻辑，也不需要去抖。
3. **窗口内每个攻击拍都重申，不是一次性**。重申本身也可能被硬直吞掉；3 秒窗口 ÷ 1.5s 攻击间隔 ≈ 补 2 次。被连续打时退化为「每次攻击都先定向」（= 参考项目 §3.1 的做法），而那正是最该定向的时候；不被打时完全不发生。

### 4.4 为什么不改 `attack_turn_direction`

它是纯几何判定，输入是信念。信念错了不是它的问题，不该在它内部打补丁。重申发生在按键层，两者职责不混。

### 4.5 配置变更

新增一项：

| 键 | 默认 | 说明 |
|---|---|---|
| `受击后重申朝向开关` | `true` | 受击后 3 秒内，每个攻击拍在按攻击键前朝当前朝向补一次 50ms 方向轻点，修正「被打后背对怪挥空」。关闭 = 完全等于 2026-08-07 之前的行为 |

窗口 3.0s 与 HP 降幅 0.01 先写常量（`FACING_REASSERT_WINDOW`、`HIT_HP_DROP_EPS`），现场需要调再暴露 —— 不预先造旋钮。

## 6. 可观测性

两处日志，都受现有 `决策日志开关` 控制：

1. 决策行（`_detect_and_act` 里那条）**加一个字段** `受击窗={Y|-}`，表示本拍是否处于受击窗口内
2. 重申发生时**单独一行** `重申朝向={L|R} 距受击={x.x}s`

分开写是因为重申发生在 `_do_attack`，晚于决策行的输出时机；硬塞进同一行会写成上一拍的值。

`grep 重申朝向` 即可数出重申次数，这是 §7.3 判据 A 的数据源，也是之后判断「还需不需要模板匹配」的依据。

## 7. 验证计划（判据事先写死）

### 7.1 纯函数单测（`tests/test_farm_logic.py`）

`hit_detected`：
- `last_hp is None` → False（首帧不判）
- 0.80 → 0.70 → True
- 0.80 → 0.795（降幅 0.005 < eps，单列抖动）→ False
- 0.80 → 0.78（降幅 0.02 > eps）→ True
- 0.70 → 0.90（喝药）→ False

**不测 eps 精确边界**：`0.8 - 0.01` 在 IEEE754 下是 `0.7900000000000001`，`0.79 < 0.7900000000000001` 为真 —— 边界断言会得到与直觉相反的结果，且随字面量写法漂移。测明确在两侧的值即可。

`should_reassert_facing`：
- `last_hit == 0.0`（从未受击）→ False，**且此断言要在小 `now`（如 5.0）下也成立**（防止实现漏掉显式哨兵判断）
- 窗口内（`now - last_hit = 1.0`，window 3.0）→ True
- 窗口外（`now - last_hit = 3.1`）→ False
- 窗口内但 `last_turn == now`（本拍已转向）→ False

### 7.2 任务级离线测试（`tests/test_farm_task_offline.py`）

前提照 memory 记的几何：`DEFAULT_CONFIG['角色名']` 为空串 → 锚点回退画面中心 **(1280, 720)**、身体 (1280, 630)、默认攻击区 x∈[980,1580] y∈[530,730]。patch `find_in_region` 无效（走不到那条通道）。

- 检测模式 + 区内有怪 + 受击窗口内 + `_facing='LEFT'` → 攻击键**之前**发出 `左移键`，`down_time == TURN_TAP_SECONDS`
- 同上但 `_facing='RIGHT'` → 发 `右移键`
- 窗口外 → 只发攻击键，无方向键
- `_facing is None` → 只发攻击键
- `受击后重申朝向开关=false` → 只发攻击键（**关闭时行为与改动前逐键一致**）
- 本拍 `attack_turn_direction` 已转向（`_last_turn == now`）→ 不重复发方向键
- `_key_sendable()` 返回 False → 不发方向键，但攻击键照发（现有行为不变）
- 重申**不修改** `_facing`

跑测试前必须确认 `screenshots/test_frames/` 是目录且含 `training_ground_full_2560x1440.png`（每次跑 GUI 都会把它删掉，备份在 `_frames_backup/`）—— 否则 30+ 用例假失败。

### 7.3 实弹验证（需管理员提权 + 游戏前台，2560×1440）

**A（门控真的触发）**：开 `决策日志开关` + `受击后重申朝向开关`，挂机 10 分钟，`grep 重申朝向 logs/ok-script.log` 行数 **> 0**。
若为 0：要么这 10 分钟没被打过（看 `受击窗=Y` 的拍数确认），要么门控写错。A 不过则 B/C/D 全部无意义，不许继续。

**B（症状改善）**：同一地图、同一时段，`受击后重申朝向开关` 开/关**交替各跑 3 轮 × 10 分钟**，记录每轮的每分钟经验增长。
通过线：**开启组的中位数 ≥ 关闭组中位数的 1.1 倍**。
若 < 1.0 倍 → §3.4 的核心假设被证伪，本方案无效，回头做附录 A 的模板匹配。
（1.1 是事先约定的通过线，不是效果预测。经验增长噪声大，交替 3 轮取中位是为了压掉刷新率波动。）

**C（没有位移副作用）**：开启后 10 分钟，决策日志里 `body_x` 的极差 **≤ 600px**。
验证 50ms 单向轻点没有累积到把角色推出站桩点。

**D（没有引入交替）**：同一组日志里，转向的反向翻转次数 **≤ 关闭组的 1.2 倍**。
设计上不该变（选边规则没动），这条是防止我判断错了。

A/B/C/D 未全部通过前，不得声称此 bug 已修复。

## 8. 明确不做

- **朝向模板匹配**（读真实朝向）—— 已实测可行，见附录 A，本次暂缓，等 §7.3 的数据再决定
- **无状态定向攻击**（每个攻击拍都定向，参考项目做法）—— 用户选择先做受击门控版本；如果 §7.3 判据 A 通过但 B 不过，这是下一个候选
- **用 `body_x` 跳变当受击信号** —— HP 下降更直接、更便宜，且不会与我们自己的走位混淆
- **改动选边规则**（`attack_turn_direction` / `seek_direction`）—— §3.3 已证明动它的方案会引入交替
- **给受击加确认帧数** —— 误报代价只是一次同向轻点，不值得

## 附录 A：朝向模板匹配可行性实测（2026-08-07，暂缓实施）

本次为回答「能不能用模板匹配识别角色面向」做的实验，**结论是可行**，数据留档以免重做。

### A.1 方法

以名字牌锚点定位 ROI（`x ∈ [a.x−90, a.x+90]`，`y ∈ [a.y−160, a.y−20]`，180×140），取其中一帧的**头+肩**子框（58×66）作模板，对每帧的 ROI 灰度图跑两次 `cv2.matchTemplate(TM_CCOEFF_NORMED)` —— 一次用模板、一次用其水平镜像，取各自最大值 `s` / `s_flip`。

样本：`dataset/raw/map1|map2|map3` 各抽帧，锚点 OCR 命中的 24 帧。模板取自 #17。

### A.2 结果

| 指标 | 数值 |
|---|---|
| 胜出分中位 | **0.883** |
| \|s − s_flip\| 中位 | **0.411** |
| 判据 `max(s,s_flip) ≥ 0.70 且 \|s − s_flip\| ≥ 0.20` | **20/24 命中，0 误判，4 弃权** |
| 命中帧的胜出分最低 / 弃权帧最高 | 0.78 / 0.45 |
| 命中帧的差值最低 / 弃权帧最高 | 0.35 / 0.055 |
| 单帧开销 | 亚毫秒（180×140 ROI × 58×66 模板 × 2 次） |

4 个弃权帧的成分：#2 / #3 / #23 是**宠物「小白雪人」把角色完全挡住**，#0 是角色被 ROI 切边。**弃权的全是真的判不了的帧，没有一个自信的错误答案。**

方向映射经放大目视核对（#17/#4 朝右，#11/#16 朝左，以靴子尖方向与刘海覆盖侧为准）：`s > s_flip` → 与模板同向。

### A.3 两个意外发现

1. **模板只取头+肩就够**。拿盾（#4）、挥杖（#19/#20/#22）等不同动画姿态照样 0.82–0.89 命中 —— 头部在各动画帧间足够稳定，**不需要一整套姿态模板库**。
2. **ROI 必须由「OCR 完整命中」的锚点定位**。第一次实验用了较小的 ROI（±32px）并接受部分匹配锚点，裁出来大量草地和宠物脸，实验作废。部分匹配（`ng咕咕`）的 OCR 框中心系统性右偏，不能用来定位角色。

### A.4 实施时的已知障碍

- 这 24 帧是 **2 秒间隔的常规打怪帧，不含「刚被击退那一瞬」**。被打时叠加伤害数字 + 击退位移 + 粉色斩击特效（已知它能让 YOLO 整只怪漏检），遮挡更重 —— 83% 的命中率**不能外推**到真正需要它的那一拍。
- 依赖锚点本拍真命中；外推/沿用的锚点会让 ROI 整体错位。
