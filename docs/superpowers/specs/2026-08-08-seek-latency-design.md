# 寻敌起步延迟 —— 根因与设计（2026-08-08）

> 现象（用户报告）：**「转向再去寻敌当中延迟很高」**。
> 结论：**不是转向慢，是寻敌起不来、起来了就被掐断。**

## 1. 结论摘要

四个独立根因，全部可在代码里指认、且有实机数据支撑：

| # | 根因 | 代码位置 | 性质 |
|---|---|---|---|
| ① | 起步寻怪只能走 `攻击间隔` 的慢拍；`寻怪刷新间隔` 只能刷新**已存在**的寻怪，不能**发起** | `MapleFarmTask.py:930-938` | 节流口径错配 |
| ② | `丢怪保持(1.0s)` 同时门控攻击**和**寻怪，制造 1 秒结构性死区 | `MapleFarmTask.py:580-603` | 去抖越界 |
| ③ | 攻击侧有去抖，寻怪侧一点都没有，一拍判失就松键 | `MapleFarmTask.py:631-643` | 不对称 |
| ④ | 同层判据与接敌区判据**基准与量都不同**，存在「攻击区罩得到却判不同层」的纵向带 | `farm_logic.py:361-364` + `MapleFarmTask.py:636-638` | 口径不一致 |

## 2. 实测证据

数据源：`logs/baseline-2026-08-08-seek.log`（2026-08-08 实机快照，`logs/` 在 `.gitignore` 里，只存本机）。判据脚本 `scripts/analyze_seek.py` 复算它即可复现下表。

### 2.1 基线（判据定义见 §5）

主基线 = `--since 14:10:00` 之后的窗口（**6668 拍 / 4211 秒 / 10 段**），即当前代码（含朝向纠正）的行为。
右侧一列是**全文件交叉验证**（**30557 拍 / 18192 秒 / 31 段**，跨越两代格式、5 小时）——结论方向一致，说明不是小样本噪声。

| 判据 | 含义 | 基线（14:10 后） | 全文件交叉验证 |
|---|---|---|---|
| A | 停手（`可打=False`）→ 起步寻怪的等待，中位 / p90 | **1.19s / 3.61s**（n=136） | 1.29s / 5.02s（n=630） |
| B | 寻怪段撑过 0.5s 的比例 | **40.4%**（344 段） | 48.8%（1573 段） |
| C | 连续空转（屏幕有怪却既不打也不追）累计占挂机时间 | **25.2%**（507 段，中位 1.47s，p90 3.85s） | 23.5%（1768 段） |
| D | `可打=True` 的拍占比 | **41.0%** | 39.2% |
| E | 决策拍间隔 中位 / p90 / max | **0.704s / 0.946s / 9.78s** | 0.702s / 0.893s / 9.78s |

补充观测（下列数字取**全文件 30557 拍**，样本更大）：

- 屏幕上有怪、却既不打也不追的拍：**20.1%**
- 处在 `丢怪保持` 窗内（`实测有怪=False` 但 `有怪=True`）的拍：**11.5%**，其中 **3310 拍**屏幕上有怪 —— 这些拍**结构性禁止寻怪**
- 「接敌区有怪 / 打不到 / 不转向 / 不追」= **0 拍** → **`转向冷却(秒)` 不是元凶**，用户直觉里的「转向慢」是被 ①②③④ 拖出来的表象
- 一个完整检测拍（模板/OCR + YOLO + 朝向观测）实测耗时 **中位 0.178s，p90 0.286s** —— 10Hz 主循环实际只跑得到 5.6Hz，这是 §3.1 定 `空闲刷新间隔` 默认值的依据
- 锚点 y 相邻拍抖动 中位 0px / p90 16px → **③ 的抖动不来自锚点**，来自怪侧（跳跃 + YOLO 框高抖动）

### 2.2 寻怪段结束归因（344 段，14:10 后窗口）

```
怪进接敌区(转攻击)                  199 = 57.8%   持续中位 0.51s
屏幕仍有怪,但判定不同层 → 直接空转     91 = 26.5%   持续中位 0.19s
怪进接敌区 但打不到                  47 = 13.7%   持续中位 0.00s   ← 起步那一拍就取消,人根本没动
屏幕上没怪了                          6 =  1.7%   持续中位 0.45s
段尾/停任务                           1 =  0.3%
```

**344 段里有 105 段（30.5%）的起步与取消发生在同一拍**（持续 0.00s），游戏里看就是原地抽搐。

### 2.3 根因 ④ 的推导（不依赖实测，纯几何）

两个判据用了不同的基准和不同的量：

| 判据 | 量 | 基准 | 半幅 |
|---|---|---|---|
| 接敌区（`mob_in_zone`） | 怪 bbox **中心** y | **身体中心** `body_y` | `攻击区高/2` = **100** |
| 同层（`same_floor`） | 怪 bbox **脚底** y | **名字牌** `anchor_y`（在 body 下方 `名字牌到身体偏移`，用户实测标定 88 / `DEFAULT_CONFIG` 90） | `寻怪同层容差` = **60** |

换算到同一坐标系（令 `h` = 怪 bbox 高）：

- 接敌区：`mob_center_y - body_y ∈ [-100, +100]`
- 同层：　`mob_center_y - body_y ∈ [88 - h/2 - 60, 88 - h/2 + 60]`

**不管 `h` 取多少，同层窗宽 120 恒小于接敌区窗宽 200。** 所以必然存在一条纵向带：怪在接敌区里（走过去就打得到），却被判「不同层」而不去追。以 `h=80` 计，这条带是 `mob_center_y - body_y ∈ [-100, -12]`，占接敌区纵向范围的 **44%**。

⚠️ 这条推导是几何必然，但**「那 20.1% 的空转拍里有多少落在这条带上」目前测不出来** —— 决策日志只记 `怪=N 区内=M`，**没有任何怪的 y**。所以计划把「补日志字段」排在所有行为改动之前（Task 1）。

## 3. 设计

### 3.1 检测节拍与攻击节拍解耦（治 ①）

现状把「多久检测一次」绑在「多久挥一刀」上：

```python
if should_attack(now, self._last_detect, cfg['攻击间隔(秒)']):        # 0.7s
    self._detect_and_act(...)
elif cfg['寻怪开关'] and self._seek_dir is not None and ...:          # 0.1s
```

`self._seek_dir is not None` 是进入快通道的**前提**，于是快通道永远只能刷新一个已经存在的寻怪。用户把 `寻怪刷新间隔` 从 0.4 调到 0.1，对「站着 → 开始追」这一步**完全无效**。

改成三态节流，纯函数 `farm_logic.should_detect`：

| 状态 | 间隔 | 理由 |
|---|---|---|
| 在打（`_last_attack_present`） | `攻击间隔(秒)` = 0.7 | 检测本来就是为下一刀服务，不必更快；**负载不回归** |
| 在追（`_seek_dir is not None`） | `寻怪刷新间隔(秒)` = 0.1 | 目标死了 / 换近了要立刻改方向 |
| 空闲（都不是） | **`空闲刷新间隔(秒)`（新增，默认 0.3）** | 这是「起步寻怪」唯一的入口 |

「在打」优先于「在追」：攻击区里有怪就是在打，不该被寻怪间隔拉快。

**默认值 0.3 的依据**：一个检测拍实测 0.178s / p90 0.286s。取 0.1 会让空闲期占满 CPU 且实际也跑不到（主循环上限 5.6Hz）；取 0.3 把起步延迟的节流分量从 0.7s 压到 0.3s，占空比从 ~28% 升到 ~40%，可控。

副产物：`elif` 分支消失 → `_last_seek_refresh` 成为死状态，一并删除。

### 3.2 寻怪起步不再被丢怪保持门控（治 ②）

`mob_present`（`丢怪保持` 去抖后）现在同时决定三件事：走接战分支、坐椅、防挂机走位。其中「走接战分支」顺带禁掉了寻怪。

去抖的正当理由（`farm_logic.py:84-99` 注释）是 YOLO 单帧 recall 0.886，一拍漏检不该松攻击键 —— **这个理由只对攻击成立**。多挥一刀空的代价，远小于多站一秒不动。

改法：给分支门一个**更短的**宽限，与攻击去抖分开。

```python
mob_present = mob_present_debounced(raw_present, now, self._last_mob_seen, cfg['丢怪保持(秒)'])      # 1.0s,喂 _last_mob_present(坐椅/走位)
seek_hold   = mob_present_debounced(raw_present, now, self._last_mob_seen, cfg['寻怪起步宽限(秒)'])  # 0.3s,决定走哪个分支
```

**攻击键本身不受影响** —— 它由 `_last_attack_present` 门控，那一路有自己的 `丢怪保持` 去抖，不经过这个分支。

**必须一并处理**「一边追一边挥」：`_detect_and_act` 的注释（`MapleFarmTask.py:574-576`）明确担心过这个错乱状态。解法是**起步即停手** —— 寻怪方向真的定下来时，把还被保持窗撑着的攻击信号立刻作废：

```python
if self._seek_dir is not None:
    self._last_attack_present = False
```

约束：`寻怪起步宽限(秒)` 必须 **< `丢怪保持(秒)`**，否则这个设计退化成原样。写进配置说明。

### 3.3 寻怪去抖（治 ③）

`seek_direction` 每拍从零重算，同层判定一抖（怪跳一下、YOLO 框高抖一下）整段就取消，`_do_seek_move` 立刻 `send_key_up`。

对称补上 `farm_logic.seek_persist` + 新配置 `寻怪保持(秒)`（默认 **0.5**）：同层怪这一拍没检出，但距上次检出还在保持窗内 → 继续按上一拍方向走。

**0.5 的依据**：小于 `丢怪保持` 的 1.0（追错方向的代价高于挥空刀，不该保持那么久），大于两个空闲检测拍（0.3×2=0.6 ≈ 一拍漏检兜得住）。按 250px/s 行走速度，最坏盲走 125px。`0` = 关掉，退回旧行为。

### 3.4 同层判据并入接敌区（治 ④）

**退休 `寻怪同层容差(像素)` 这个配置，同层直接由接敌区的纵向范围定义。**

```python
def seek_direction(centres, body_x, zone, current_dir=None):
    """同层 = 怪中心落在接敌区的纵向范围内(与 mob_in_zone 完全同口径)。"""
    y0, y1 = zone[1], zone[3]
    same = [x for x, y in centres if y0 <= y <= y1]
```

语义变得自洽：**寻怪 = 「走过去就打得到、但现在水平够不着」的怪**。留着一个独立旋钮，就是把「口径不一致」这个根因本身留在配置里。

代价（如实记录）：
- 这是一个**破坏性签名变更**（`(mob_entries, body_x, player_feet_y, tolerance, current_dir)` → `(centres, body_x, zone, current_dir)`），调用方从传「怪脚底 y」改成传「怪中心 y」，`tests/test_farm_logic.py` 有 ~10 个用例要重写。
- 判据放宽（等效半幅 60 → 100）后，**理论上更容易追到别的平台的怪**。但接敌区本来就罩着这个范围 —— 落在里面的怪本来就会被攻击，走过去打它是一致的，不是新增风险。
- 老配置文件里残留的 `寻怪同层容差(像素)` 键无害（`config` 是普通 dict，多余键不参与任何分支），无需迁移。

`farm_logic.same_floor` 改完若无调用方，一并删除（不留死代码）。

## 4. 不做什么

- **不动 `转向冷却(秒)`。** 实测「区内有怪 / 打不到 / 不转向 / 不追」= 0 拍，它没卡住任何东西。动它会重新打开 2026-08-07 已经压住的「原地左右扭」（`farm_logic.py:102-109` 实测 17 次转向 12 次是反向）。
- **不动 `丢怪保持(秒)`。** 它对攻击键是对的，问题在于被借去门控寻怪。
- **不动攻击键节奏 / 有向攻击区 / 朝向纠正。** 与本问题无关，且都是刚验收过的机制。
- **不把检测拍无条件提速到 0.1s。** 主循环实测上限 5.6Hz，无条件提速只会把 CPU 打满、把「在打」这 41% 的时间也拖进高负载，而那部分本来没问题。

## 5. 验收判据（先写死，实测之前不许改）

改完跑 **≥ 20 分钟**实机（开 `决策日志开关`），用 `scripts/analyze_seek.py` 复算。判据定义特意只依赖 `可打=` 和 `寻怪=` 两个字段 —— 它们在本次改动前后语义不变（`有怪=` 的门控作用被 §3.2 改掉了，不能拿来当尺子）。

| 判据 | 定义 | 基线 | 通过线 |
|---|---|---|---|
| **A** | 停手→起步寻怪等待：从「`可打=False` 且 `怪>0` 且 `寻怪=-`」的第一拍，到「`寻怪≠-`」的那一拍 | 中位 1.19s / p90 3.61s | **中位 ≤ 0.50s 且 p90 ≤ 1.50s** |
| **B** | 寻怪段撑过 0.5s 的比例 | 40.4% | **≥ 65%** |
| **C** | 连续空转（`可打=False` 且 `寻怪=-` 且 `怪>0`）累计占挂机时间 | 25.2% | **≤ 12%** |

## 6. 风险与回退

| 风险 | 触发信号 | 回退 |
|---|---|---|
| 空闲期 CPU 打高，主循环被拖慢 | 判据 E 不过 | `空闲刷新间隔(秒)` 调回 0.7（= 旧行为） |
| 怪在区边缘擦进擦出，角色「走一步打一下」 | 判据 D 掉，或肉眼看到抖 | `寻怪起步宽限(秒)` 调大（上限 `丢怪保持(秒)`，取等即旧行为） |
| 盲走过头、追丢 | 判据 B 高但 D 掉 | `寻怪保持(秒)` 调小，`0` = 旧行为 |
| 追到别的平台 / 掉台子 | 肉眼 + overlay 截图 | §3.4 无旋钮可退，只能 `git revert` 该任务的提交 |

前三个风险都留了「调回默认即旧行为」的退路；§3.4 没有，所以它在计划里排在最后、且带独立的 E2E 截图验收。
